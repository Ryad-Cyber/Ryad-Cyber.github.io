CAS Nº1Lab SOC Elastic Security

Un environnement de détection monté en laboratoire : 4 règles personnalisées, testées à l'aide d'attaques simulées sur des machines Linux et Windows.

Objectif
Travailler la détection sur mes propres données, plutôt que sur des jeux de logs préparés.
Résultat
4 règles validées sur 3 scénarios d'attaque, un guide d'investigation par règle, et le lab documenté sur GitHub.

Contexte

Je voulais travailler la détection sur mes propres données, plutôt que sur des jeux de logs préparés. J'ai donc monté un environnement de détection en laboratoire, de la collecte des événements à l'investigation des alertes, puis simulé des attaques sur des machines Linux et Windows pour écrire et tester les règles correspondantes.

Ce que j'ai fait

  1. Déployé la stack Elasticsearch + Kibana avec Fleet, et enrôlé des Elastic Agents sur Ubuntu, Windows 11 et un contrôleur de domaine Windows Server.
  2. Instrumenté les postes Windows avec Sysmon et activé le Script Block Logging PowerShell pour obtenir les événements nécessaires aux détections.
  3. Écrit et testé 4 règles de détection couvrant 3 scénarios d'attaque simulés, puis ajusté les règles pour limiter les faux positifs.
  4. Rédigé un guide d'investigation par règle : ce que l'alerte signifie, les champs à vérifier en priorité, et les étapes de qualification.
  5. Documenté l'ensemble du lab sur GitHub pour qu'il soit reproductible.

Les 3 scénarios de détection

  • SSH Brute Force (Linux)

    Détection des échecs d'authentification répétés depuis une même source, puis corrélation en EQL de la séquence « échecs multiples suivis d'une connexion réussie » — le signal qui distingue une tentative d'une compromission probable.

  • PowerShell obfusqué (Windows 11)
    MITRE ATT&CK T1059.001

    Détection des commandes encodées en base64 passées à PowerShell, à partir des blocs de script capturés par le Script Block Logging.

  • Password Spray sur Active Directory (Windows Server)
    MITRE ATT&CK T1110.003

    Règle Threshold en KQL sur l'Event ID 4625 du contrôleur de domaine, agrégée par source.ip avec une cardinalité sur user.name : c'est ce critère qui sépare un password spray — beaucoup de comptes testés, peu de tentatives sur chacun — d'un brute force classique sur un seul compte.

Objectif
Vérifier de bout en bout qu'un SIEM open source détecte réellement des attaques, pas seulement qu'il collecte des logs.
Résultat
2 règles personnalisées mappées MITRE ATT&CK, testées par brute force SSH et scans Nmap, puis comparées à Elastic Security.

Contexte

Déployer un SIEM open source sur une infrastructure hétérogène de plusieurs machines virtuelles, et vérifier de bout en bout qu'il détecte réellement des attaques — pas seulement qu'il collecte des logs.

Ce que j'ai fait

  1. Installé le manager Wazuh et déployé les agents sur des machines Linux et Windows, avec centralisation des journaux.
  2. Écrit 2 règles de détection personnalisées, mappées sur le framework MITRE ATT&CK.
  3. Testé chaque règle à l'aide de scénarios en laboratoire — brute force SSH et scans Nmap — puis vérifié la remontée des alertes dans le tableau de bord.
  4. Comparé le comportement de Wazuh à celui d'Elastic Security sur des scénarios équivalents, pour comprendre ce que chaque outil rend facile ou difficile.

Scan, attaque simulée et détection

  • Scan réseau avec Nmap
    MITRE ATT&CK T1046

    Reconnaissance initiale de la machine cible pour identifier les services exposés avant de simuler une attaque.

  • Brute force SSH avec Hydra
    MITRE ATT&CK T1110

    Tentative de brute force contre le service SSH identifié, pour générer les échecs d'authentification que la règle de détection doit remonter.

  • Alertes et règle personnalisée

    Les échecs d'authentification SSH et PAM remontent dans le tableau de bord, aux côtés de la règle personnalisée 100002 qui qualifie la création d'un compte utilisateur suspect — visible directement sur la carte du projet.

CAS Nº4Pentest Linux — VulnHub DC-4

Compromission de bout en bout d'une machine Linux VulnHub en laboratoire isolé : reconnaissance, accès initial, mouvement latéral et élévation de privilèges jusqu'à root.

  • Kali Linux

Lire le cas en détailReplier le détail↗
Objectif
Conduire un pentest méthodique sur DC-4 (VulnHub) dans un lab isolé, de la reconnaissance jusqu'à l'obtention de root.
Résultat
Accès root validé : compte UID 0 créé via une règle Sudo trop permissive, puis lecture du flag dans /root/flag.txt.

Présentation et objectifs

DC-4 est une machine Linux volontairement vulnérable publiée sur VulnHub. Je l'ai exécutée dans un laboratoire isolé, depuis Kali Linux, pour travailler une chaîne d'attaque complète : reconnaissance des services, accès initial, énumération locale, mouvement latéral et élévation de privilèges.

Méthodologie et chaîne d'attaque

  • Reconnaissance
    MITRE ATT&CK T1046

    Scan Nmap de la cible : identification des services SSH (port 22) et HTTP (port 80, nginx — interface « System Tools »).

  • Accès initial
    MITRE ATT&CK T1110

    Test du formulaire d'authentification web avec Hydra, puis connexion SSH avec le compte jim. L'interface web « System Tools » confirme l'accès authentifié obtenu.

  • Énumération locale et mouvement latéral
    MITRE ATT&CK T1552

    Lecture de /var/mail/jim : un message laisse apparaître un mot de passe transmis en clair pour le compte charles. Passage de jim à charles (les secrets ne sont pas reproduits ici).

  • Élévation de privilèges
    MITRE ATT&CK T1548.003

    sudo -l montre que charles peut exécuter /usr/bin/teehee en tant que root sans mot de passe. Cette autorisation a servi à ajouter une entrée dans /etc/passwd et à créer un compte disposant de l'UID 0.

Résultats obtenus

  • Chaîne d'attaque complète en laboratoire isolé, de la reconnaissance à root.
  • Validation des privilèges avec id (UID 0), puis lecture de /root/flag.txt.
  • Deux failles principales exploitées : exposition d'identifiants et règle Sudo trop permissive.

Analyse des failles

  • Exposition d'identifiants : un mot de passe transmis en clair dans la messagerie locale a permis le mouvement latéral vers charles.
  • Règle Sudo trop permissive : teehee exécutable en root (NOPASSWD) a permis d'écrire dans /etc/passwd et de créer un compte UID 0.

Recommandations de remédiation

  • Ne jamais transmettre de mots de passe en clair (messagerie, tickets, fichiers partagés) ; privilégier un gestionnaire de secrets et la rotation immédiate en cas d'exposition.
  • Restreindre les règles Sudo au strict nécessaire ; éviter NOPASSWD sur des binaires capables d'écrire des fichiers système.
  • Renforcer l'authentification du formulaire web (limitation de débit, verrouillage de compte, mots de passe robustes) pour freiner le brute force.
  • Surveiller les accès SSH, les lectures de boîtes mail et les modifications de /etc/passwd.

Compétences et outils mobilisés

Kali Linux, Nmap, Hydra, SSH, énumération Linux, analyse de règles Sudo et méthodologie de pentest offensif en environnement isolé.

Contexte et objectif

Projet pratique réalisé dans le cadre de la formation AWS Academy Cloud Foundations pour manipuler les composants fondamentaux d’une infrastructure AWS et découvrir leur sécurité. Il s’agit d’un environnement de formation, sans audit professionnel ni infrastructure de production.

Réalisations techniques

  1. Autorisations IAM. Analyse et configuration de EC2-Admin-Policy au format JSON : ec2:Describe*, ec2:StartInstances et ec2:StopInstances. Objectif : comprendre la granularité des permissions et le principe du moindre privilège.
  2. Architecture VPC. Étude de Lab VPC — 10.1.0.0/16, de Public Subnet 1 — 10.1.11.0/24 et de la table de routage publique (Public Route Table, affichée « Public » sur la capture). Objectif : comprendre la segmentation, le routage et la connectivité.
  3. EC2 et Security Groups. Manipulation de LabHost et Bastion Host ; observation et configuration des règles réseau entrantes, dont SSH sur TCP/22. Objectif : comprendre l’administration des instances et le filtrage réseau.

Ce que ce laboratoire m’a appris

Relier les permissions IAM, l’organisation du réseau et les règles des Security Groups. Distinguer une configuration d’apprentissage d’une configuration réellement durcie ; notamment, des actions IAM limitées ne suffisent pas si le périmètre des ressources reste large.
