CAS Nº1 — Lab SOC Elastic Security

2026 Projet personnel Elasticsearch, Kibana, Elastic Security, Fleet, Elastic Agent, Sysmon, KQL, EQL, MITRE ATT&CK, Windows Server / AD, Ubuntu

Contexte

Je voulais travailler la détection sur mes propres données, et pas sur des jeux de logs préparés. J'ai donc construit un SOC complet en laboratoire — collecte, règles, investigation — puis joué de vraies attaques contre des machines Linux et Windows pour écrire et éprouver les détections correspondantes.

Ce que j'ai fait

  1. Déployé la stack Elasticsearch + Kibana avec Fleet, et enrôlé des Elastic Agents sur Ubuntu, Windows 11 et un contrôleur de domaine Windows Server.
  2. Instrumenté les postes Windows avec Sysmon et activé le Script Block Logging PowerShell pour obtenir les événements nécessaires aux détections.
  3. Écrit et validé 4 règles de détection couvrant 3 scénarios d'attaque, chacune déclenchée par une attaque simulée puis ajustée pour limiter les faux positifs.
  4. Rédigé un guide d'investigation par règle : ce que l'alerte signifie, les champs à vérifier en priorité, et les étapes de qualification.
  5. Documenté l'ensemble du lab sur GitHub pour qu'il soit reproductible.

Les 3 scénarios de détection

  • SSH Brute Force (Linux)

    Détection des échecs d'authentification répétés depuis une même source, puis corrélation en EQL de la séquence « échecs multiples suivis d'une connexion réussie » — le signal qui distingue une tentative d'une compromission probable.

  • PowerShell obfusqué (Windows 11)
    MITRE ATT&CK T1059.001

    Détection des commandes encodées en base64 passées à PowerShell, à partir des blocs de script capturés par le Script Block Logging.

  • Password Spray sur Active Directory (Windows Server)
    MITRE ATT&CK T1110.003

    Règle Threshold en KQL sur l'Event ID 4625 du contrôleur de domaine, agrégée par source.ip avec une cardinalité sur user.name : c'est ce critère qui sépare un password spray — beaucoup de comptes testés, peu de tentatives sur chacun — d'un brute force classique sur un seul compte.

CAS Nº2 — Lab Wazuh (SIEM) multi-VM

05/2026 Projet académique Wazuh, VMware, Linux, Windows, MITRE ATT&CK, Nmap, Syslog

Contexte

Déployer un SIEM open source sur une infrastructure hétérogène de plusieurs machines virtuelles, et vérifier de bout en bout qu'il détecte réellement des attaques — pas seulement qu'il collecte des logs.

Ce que j'ai fait

  1. Installé le manager Wazuh et déployé les agents sur des machines Linux et Windows, avec centralisation des journaux.
  2. Écrit 2 règles de détection personnalisées, mappées sur le framework MITRE ATT&CK.
  3. Validé chaque règle par attaque simulée — brute force SSH et scans Nmap — et vérifié la remontée des alertes dans le dashboard.
  4. Comparé le comportement de Wazuh à celui d'Elastic Security sur des scénarios équivalents, pour comprendre ce que chaque outil rend facile ou difficile.

Projet académique — documentation interne, dépôt non public.

CAS Nº3 — KASBAH 2026 — gestion de crise cyber

09/2026 EMSI × CyberSup

Contexte

Compétition de gestion de crise cyber sur trois jours : une cyberattaque simulée contre une organisation, à traiter en temps réel avec une information partielle et des décisions à prendre vite.

Ce que j'ai fait

  • Membre de la cellule Direction : arbitrage des priorités pendant toute la durée de la crise.
  • Décisions de confinement mises en balance avec la continuité d'activité.
  • Coordination et communication avec les cellules techniques et les interlocuteurs externes.
  • Retour d'expérience utile pour un analyste : une alerte n'a de valeur que si elle est qualifiée et transmise clairement à ceux qui décident.

Compétences mobilisées

  • Gestion de crise
  • Coordination
  • Prise de décision
  • Communication
  • Travail sous pression
