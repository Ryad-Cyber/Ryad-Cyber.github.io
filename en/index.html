Read the case in detailCollapse the detail↗
Objective
Practise detection on my own data rather than on prepared log datasets.
Outcome
4 rules validated across 3 attack scenarios, an investigation guide per rule, and the whole lab documented on GitHub.

Detection rules overview

Context

I wanted to practise detection on my own data rather than on prepared log datasets. So I built a detection environment in a lab, from event collection through to alert investigation, then simulated attacks on Linux and Windows machines to write and test the matching rules.

What I did

  1. Deployed the Elasticsearch + Kibana stack with Fleet, and enrolled Elastic Agents on Ubuntu, Windows 11 and a Windows Server domain controller.
  2. Instrumented the Windows hosts with Sysmon and enabled PowerShell Script Block Logging to capture the events the detections depend on.
  3. Wrote and tested 4 detection rules covering 3 simulated attack scenarios, then tuned the rules to limit false positives.
  4. Wrote an investigation guide for every rule: what the alert means, which fields to check first, and the triage steps.
  5. Documented the whole lab on GitHub so that it can be reproduced.

The 3 detection scenarios

  • SSH brute force (Linux)

    Detects repeated authentication failures from a single source, then correlates in EQL the sequence "multiple failures followed by a successful login" — the signal that separates an attempt from a likely compromise.

  • Obfuscated PowerShell (Windows 11)
    MITRE ATT&CK T1059.001

    Detects base64-encoded commands passed to PowerShell, using the script blocks captured by Script Block Logging.

  • Active Directory password spray (Windows Server)
    MITRE ATT&CK T1110.003

    A KQL threshold rule on Event ID 4625 from the domain controller, aggregated by source.ip with a cardinality condition on user.name: that condition is what separates a password spray — many accounts tried, few attempts on each — from a classic brute force against a single account.

CASE Nº3Web Application Penetration Testing — OWASP Juice Shop

Targeted manual assessment of a local Juice Shop instance: five validated findings across search, access control and REST API behavior.

  • Burp Suite
  • SQL injection
  • XSS
  • IDOR
  • REST API
  • JWT
  • Business logic
  • Docker
Read the case in detailCollapse the detail↗
Scope
Selected Juice Shop features and REST endpoints in a local training lab.
Result
Five validated findings, with evidence and remediation in the security report.

Context and method

OWASP Juice Shop, an intentionally vulnerable application, was deployed with Docker Desktop on Windows. I manually inspected requests and responses using Burp Suite Community Edition (Proxy, HTTP History and Repeater). This was a targeted assessment, not an exhaustive audit.

Validated findings

  1. SQL injection. A crafted product search query bypassed filtering and returned normally excluded records.
  2. XSS. A crafted search input executed JavaScript; the exact reflected, stored or DOM classification was not established.
  3. Broken access control / IDOR. Changing a basket identifier allowed a read of another user’s basket. The attempted write was rejected.
  4. Information disclosure. An API error response exposed a stack trace and internal implementation details.
  5. Business logic / input validation. The REST API accepted and stored a negative basket quantity. No payment amount manipulation was demonstrated.

Additional tests

Missing and invalid JWTs were rejected with 401 responses in the tested basket requests. I also checked authorization, HTTP headers, input validation and REST traffic; these checks do not establish other exploitable vulnerabilities.

Remediation priorities

  • Use parameterized queries and enforce product visibility on the server.
  • Encode output according to context and avoid unsafe HTML insertion.
  • Check object-level authorization on each basket read; validate positive quantities server-side.
  • Return generic client errors and keep stack traces in server logs.

Read the case in detailCollapse the detail↗
Objective
Assess a local Ollama chatbot (llama3.2:3b) against prompt injection, jailbreak attempts, system prompt disclosure and insecure output handling.
Outcome
3 of 4 test categories showed an exploitable issue, including an injection that persisted across later turns; classic jailbreak framing was blocked.

Context

A fully local personal lab, on hardware I control, with no third-party, production or internet-facing system involved. The "SupportBot" chatbot runs on an Ollama llama3.2:3b model with a custom system prompt containing fictional business data (a VIP code, an internal admin email) used as disclosure markers.

What I did

  1. Deployed llama3.2:3b via Ollama with a custom system prompt holding fictional marker data.
  2. Manually tested 4 risk categories — system prompt disclosure, direct prompt injection, insecure output handling and jailbreak resistance — against the OWASP Top 10 for LLM Applications (2025) and MITRE ATLAS.
  3. Documented every prompt, response and verdict in an evidence report with screenshots.
  4. Mapped each result to OWASP categories (LLM01, LLM05, LLM07) and MITRE ATLAS techniques (AML.T0051, AML.T0054, AML.T0056).

Results of the 4 tests

  • System prompt disclosure
    OWASP LLM07 · MITRE AML.T0056

    Direct requests to repeat or ignore instructions were refused, but a "developer/debug mode" framing leaked fictional fields marked sensitive in the system prompt.

  • Prompt injection, with persistence
    OWASP LLM01 · MITRE AML.T0051

    A direct injected instruction was blocked, but an injection disguised as a conversation-boundary delimiter with a fake SYSTEM: role overrode the assistant's identity — and that override persisted into a later, unrelated-looking turn.

  • Insecure output handling
    OWASP LLM05

    The model neutralized an injected XSS payload in generated HTML, but returned sudo rm -rf /var/log/* as a ready-to-run command for "cleaning up logs," with only a verbal caution.

  • Jailbreak resistance
    MITRE AML.T0054

    Both a "DAN" persona override and a fictional-narrative framing were refused — the one category out of four where the model's guardrails held.

Annotated screenshots

Limitations

Manual, exploratory testing (3-3-2-2 prompts across categories), with no automated LLM red-teaming tool. Results reflect a single configuration (llama3.2:3b with one system prompt) at one point in time, and do not necessarily generalize to a different model or system prompt.

Local infrastructure deployed with Terraform and Docker: Nginx frontend, HTTP Echo backend, network segmentation and container hardening.

Read the case in detailCollapse the detail↗
Scope
Local Terraform and Docker lab; no AWS services
Outcome
Frontend bound to 127.0.0.1:8080; backend without a published port; non-root execution, restricted privileges, network isolation and limited host exposure validated.

Architecture and segmentation

Terraform provisions an Nginx frontend and an HTTP Echo backend across two Docker networks. The frontend joins both networks; the backend joins only the internal network. The frontend can reach the backend without publishing a backend port on the host.

Security controls

  • Non-root execution: UID 101 for Nginx and UID 65532 for HTTP Echo.
  • No-new-privileges enabled and all additional Linux capabilities dropped.
  • Memory limits of 128 MiB for the frontend and 64 MiB for the backend; read-only HTML mount.

Documented validation

Docker checks in the repository verify UIDs, security options, the localhost binding on port 8080, the internal network and the absence of a published backend port. Frontend HTTP availability and frontend-to-backend communication were also checked. This segmentation reduces exposure but does not guarantee complete isolation from the host.

CASE Nº7CryptoKit — Python cryptography toolkit

Command-line tool written in Python: AES-256-GCM file encryption, file digests, RSA digital signatures and X.509 certificates, with the historical ciphers clearly separated from the modern functionality.

  • Python
  • cryptography
  • AES-256-GCM
  • PBKDF2-HMAC
  • RSA-PSS
  • X.509
  • argparse
  • pytest
Read the case in detailCollapse the detail↗
Objective
Build a cryptography tool that is actually usable on the command line, relying on proven modern primitives rather than hand-written ones.
Outcome
A complete, tested toolkit (19 passing automated tests): authenticated file encryption, file digests, digital signatures and X.509 certificates, published open source.

Overview and objectives

A personal project built to work with real cryptographic primitives rather than staying at a theoretical level, with an eye toward roles focused on secure deployment, authentication and certificate management. CryptoKit brings together, under a single command-line interface, educational historical ciphers and modern cryptographic functionality that are clearly kept apart.

Features

  1. Historical ciphers. Caesar and Vigenère, with a bruteforce mode that prints all 26 possible Caesar shifts — a concrete illustration of why it offers no real protection.
  2. File encryption. AES-256-GCM (authenticated encryption), with a key derived from a passphrase via PBKDF2-HMAC-SHA256; any tampering with the encrypted file makes decryption fail instead of silently producing corrupted data.
  3. File digests. Computing and verifying SHA-256/384/512, reading files in chunks for large inputs.
  4. Digital signatures. RSA-2048 key-pair generation, file signing and verification (PSS padding, SHA-256).
  5. X.509 certificates. Generating self-signed certificates for a test environment, and inspecting an existing certificate (subject, issuer, validity, key size).

Technical choices

  • The cryptography library (implementations linked against OpenSSL) rather than hand-written primitives.
  • AES-256-GCM rather than an unauthenticated mode: any tampering with the encrypted file is detected.
  • Key derivation with 390,000 PBKDF2-HMAC-SHA256 iterations, matching the OWASP (2023) recommendation.
  • PSS padding rather than PKCS#1 v1.5 for signatures, the currently recommended choice for RSA.
  • Code organised into independent modules (classical, modern, hashing, signatures, certificates), kept separate from the command-line interface.

Annotated screenshot

Results and verification

  • 19 passing automated tests (pytest): encrypt/decrypt round trips, detecting an incorrect passphrase, detecting a tampered file, digest consistency against hashlib, valid and invalid signatures, certificate generation/inspection.
  • The six main commands were run manually and checked end to end (text encrypted/decrypted, file encrypted/decrypted, digest computed and verified, signature generated and verified, certificate generated and inspected).
  • Repository published open source, with an MIT licence and complete technical documentation.

Acknowledged limitations

A learning and demonstration project, not independently audited: not to be used to protect real data in production. The encrypted file format is specific to this project and is not interoperable with other tools; the private keys generated by the demo commands are not encrypted on disk; the generated certificates are self-signed, with no recognised certificate authority behind them.

CASE Nº8Linux pentest — VulnHub DC-4

Isolated lab pentest: web access, command injection, a reverse shell, local progression and privilege escalation to root.

  • Kali Linux
  • Nmap
  • Burp Suite
  • Netcat
  • SSH
  • Linux
  • Sudo
  • VulnHub
  • MITRE ATT&CK
Read the case in detailCollapse the detail↗
Objective
Run a methodical pentest of DC-4 (VulnHub) in an isolated lab, from reconnaissance through to root.
Outcome
Root access validated: a UID 0 account created via an overly permissive Sudo rule, then the flag read from /root/flag.txt.

Overview and objectives

DC-4 is a deliberately vulnerable Linux machine published on VulnHub. I ran it in an isolated lab from Kali Linux to practise a full attack chain: reconnaissance, web access, command injection, a www-data shell, local progression and privilege escalation.

Methodology and attack chain

  • Reconnaissance
    MITRE ATT&CK T1046

    Nmap scan of the target: SSH (port 22) and HTTP (port 80, nginx — « System Tools » interface) identified as open.

  • Web authentication
    MITRE ATT&CK T1110

    Used Burp Suite Intruder to intercept HTTP requests to login.php and test authentication in the lab, gaining access to the “System Tools” administrative interface.

  • Command injection and reverse shell
    MITRE ATT&CK T1059.004

    In Burp Suite Repeater, modified a POST request to /command.php to exploit command injection. The HTTP 504 response alone does not prove access; the Netcat screenshot shows the incoming connection, and id confirms a shell as www-data.

  • Local enumeration and progression
    MITRE ATT&CK T1552.001

    Local progression to the jim account, whose mailbox /var/mail/jim holds a password sent in plaintext — enough to move on to the charles account.

  • Privilege analysis
    MITRE ATT&CK T1548.003

    sudo -l showed that charles may run /usr/bin/teehee as root without a password.

  • Privilege escalation and root
    MITRE ATT&CK T1548.003

    The excessive Sudo permission allowed an entry to be appended to /etc/passwd via teehee, creating a UID 0 account. Root access was then validated and the final flag read.

Results

  • Attack chain documented: network reconnaissance, web access, command injection, www-data shell, local progression and root.
  • Privileges validated with id (UID 0), then /root/flag.txt read.
  • Findings exploited: command injection, exposed credentials and an overly permissive Sudo rule.

Vulnerability analysis

  • Command injection: the web interface executes user-controlled input through /command.php, providing system access as www-data.
  • Exposed credentials: a password sent in cleartext via local mail enabled lateral movement to charles.
  • Overly permissive Sudo rule: teehee runnable as root (NOPASSWD) allowed writing to /etc/passwd and creating a UID 0 account.

Remediation recommendations

  • Prevent web input from reaching system command execution; validate parameters strictly and limit the service account's privileges.
  • Never send passwords in cleartext (mail, tickets, shared files); use a secrets manager and rotate immediately if exposed.
  • Restrict Sudo rules to the minimum required; avoid NOPASSWD on binaries that can write system files.
  • Harden the web login (rate limiting, account lockout, strong passwords) to slow brute force.
  • Monitor SSH access, mailbox reads and changes to /etc/passwd.

Skills and tools used

Kali Linux, Nmap, Burp Suite Intruder and Repeater, Netcat, Linux enumeration, Sudo rule analysis and offensive pentest methodology in an isolated environment.

CASE Nº11SOC Anomaly Detection with Isolation Forest

Unsupervised anomaly detection across 2.6 million multi-network SOC alerts: time windowing, Isolation Forest, a 99th-percentile threshold, incident grouping and tree-path explainability.

  • Python
  • pandas
  • scikit-learn
  • Isolation Forest
  • Anomaly Detection
  • Unsupervised Machine Learning
  • SOC
Read the case in detailCollapse the detail↗
Objective
Reduce alert noise and surface the most suspicious time windows in the AIT Alert Data Set (eight simulated enterprise networks), without relying on labels upfront.
Outcome
41 windows flagged in the monitored period, 23 of which contained a labelled attack step (56.1% precision); 32.4% of monitored intrusion windows recovered; 21 incidents grouped across the eight networks.

Context

Academic work completed at EMSI, in the AI for Cybersecurity module. The dataset combines alerts already generated by Wazuh, Suricata and AMiner across eight simulated networks, with documented attack steps — these tools were not deployed as part of this project: the work focuses on analysing the alerts they produced.

What I did

  1. Loaded and prepared 2.6 million alerts from the eight networks, identifying the originating detector (Wazuh, Suricata, AMiner).
  2. Built 10-minute windows per network and host, and applied a log1p transform to alert counts.
  3. Trained an unsupervised IsolationForest on each network's first-day windows, used as the "normal" baseline.
  4. Set the detection threshold at the 99th percentile of first-day scores, rather than an arbitrary value.
  5. Grouped and ranked flagged windows into incidents, then explained the most suspicious windows from the trees' decision paths.
  6. Compared results against the dataset's labelled attack steps, and studied the effect of hyperparameters (sample size, number of trees).

Detection results

  • Threshold used: 0.493 (99th percentile of first-day scores).
  • 41 windows flagged in the monitored period; 23 contained at least one labelled attack step.
  • Precision of flagged windows: 56.1% — share of monitored intrusion windows recovered: 32.4%.
  • 21 incidents grouped across the eight networks, ranked by number of hosts involved and cumulative score.

Case study — the wilson network

On the wilson network, three incidents were flagged and ranked. The top-ranked incident matches the attack actually documented on that network (service scan → wpscan → dirb → webshell → password cracking → sudo escalation), affecting seven hosts. But detection remains partial: some attack steps, such as password cracking, were not recovered on any of the eight networks.

Annotated screenshots

Limitations

Figures are specific to this dataset and configuration (window size, 99th-percentile threshold): they are not a guarantee of performance in a real environment. The first-day baseline is assumed "normal" without independent verification. Detection remains partial: several documented attack steps go unflagged on one or more networks.
